# 線上單堂轉方案＋「方案」獨立管理 — 設計規格

- 日期：2026-11-14
- 狀態：業主已確認方向與八條規則（見「業主確認的規則」）；標「我的判斷」的項目由撰寫者決定，待業主閱後確認。已經過一輪實作者角度的審查（2026-11-14），審查提出的五個問題都已寫進本文（退款只能一次、已付款不能改掛、折扣碼用量、先用順序、退款入口）。第一階段已實作，見 plans/2026-11-14-online-single-as-package.md
- 相關規格：`2026-06-24-coach-package-calendar-booking-design.md`（方案與登錄）、`2026-06-12-booking-payment-flow-design.md`（付款核對）、`2026-07-03-admin-payroll-tab-design.md`（薪資）、`2026-07-04-renewal-reminders-design.md`（續購提醒）、`2026-06-24-my-schedule-packages-design.md`（客人端我的方案）

## 為什麼

業主在後台「會員管理」打開會員資料時，方案那一區只看得到教練替客人開的方案。客人自己在線上預約的一對一單堂課（例如周善美）不在裡面，畫面寫「尚無方案」，等於這位客人買過什麼、上過幾堂在這裡看不出來。

業主要的結果：

1. 線上單堂課也是方案——會員的方案區看得到一張一張的單堂方案卡。
2. 舊資料補齊——所有會員重新掃一次，沒記進方案的一對一單堂課補登。
3. 「方案」在後台能獨立出來管理，不必一位一位會員點開。
4. 連動到的地方都要處理好，不能因此出錯。

## 現況

- `customer_packages` 已經是獨立資料表（會員、類型 1on1／1on2、總堂數、剩餘堂數、金額、到期日、備註、折扣碼、建立者、建立時間、作廢時間）。`bookings.package_id` 指向它，NULL 代表「不是方案的預約」。
- 線上預約（`POST /api/public/bookings` → `createBookingAnon`）只建立 `bookings`：`package_id` NULL、`original_amount`＝定價（一對一 1500／一對二 2000，後台可調）、`discount_amount`／`discount_code` 另記、`paid_at` NULL（待核對，管理者核對後才有值）。管理者用同一個入口替客人補登過去的課，走的也是這條路。
- 教練「登錄預約」（`createCoachRegister`）一律要選方案，登錄當下就蓋 `paid_at`，`original_amount`＝方案單價。
- 公開端現在只有單筆預約，沒有循環入口。舊資料裡可能有帶 `recurring_group_id` 的散客循環預約。
- 後台只在會員編輯彈窗的「方案（套餐）」區顯示方案（`admin.js` `renderMemberPackages` → `GET /api/coach/packages?memberId=&includeArchived=1`），沒有跨會員的方案頁。
- 薪資明細把 `package_id` NULL 的堂標成「散客」，有方案的標「方案」；金額一律是 `original_amount − discount_amount`。

## 目標

- 每一筆線上單堂預約都有一張對應的「一堂方案」，建立預約時自動產生。
- 既有未取消的線上單堂預約全部補上對應方案，補登不改變任何金額、不發任何通知。
- 會員方案區顯示線上單堂卡，卡上有上課時間、教練、金額、付款狀態。
- 後台新增「方案」頁籤，可跨會員搜尋、篩選、查看與管理方案。
- 所有原本依「有沒有方案」分流的地方，結果與上線前一致，或依下面規則明確改變。

## 不做的事

- 團體課不動。
- 線上預約流程、價格、折扣碼、客人看到的畫面不變。
- 付款核對流程（待核對／已核對／退款）不變。
- 薪資金額算法不變。
- 續購提醒只發 10 堂方案的規則不變。
- 循環登錄不自動接續下一筆方案（#150 的決定維持）。

## 絕對不能發生的事

- 薪資任何一期的數字因為補登而改變。
- 客人或教練因為補登收到通知。
- 教練登錄時被一張來路不明的單堂方案卡住，選不了客人的 10 堂方案。
- 補登重跑後產生重複的方案。
- 已付款的錢對應到兩堂可上的課，或一堂都沒有。

## 業主確認的規則

以下八條業主 2026-11-14 已確認：

1. **建立時機**：線上預約送出當下就建一張一堂的方案並掛上那堂課。卡片顯示上課時間、教練、金額、付款狀態（待核對／已核對／已退款）。
2. **取消時**：還沒付款的，那張單堂方案一起作廢。已付款的，保留成「剩 1 堂」可以改約，等管理者按退款才作廢。
3. **舊方案先用**：只有「已付款又取消」留下的那 1 堂會排進先用順序。
4. **續購提醒**：線上單堂不算「已買新方案」，10 堂方案剩 1 堂照樣提醒。
5. **客人端「我的方案」**：不顯示單堂卡。
6. **薪資**：金額算法不變，明細來源仍標「散客」。
7. **補登範圍**：過去和未來所有未取消的線上單堂都補；已取消的不補。
8. **上線前**：先用業主已登入的後台分頁唯讀掃一次正式站，列出會補幾筆、各是什麼狀態，業主確認數字後才合併。

## 資料庫結構

不新增資料表。變更兩處：

### `customer_packages.source`

```sql
source TEXT NOT NULL DEFAULT 'staff' CHECK (source IN ('staff', 'online'))
```

- `staff`：教練或管理者開立的方案（現有全部方案）。
- `online`：線上單堂預約自動產生的一堂方案。
- 新資料庫寫進 `schema.js` 的 `CREATE TABLE`；既有資料庫用 `connection.js` 的 `addColumnIfMissing` 補欄位，既有列自動取得預設值 `staff`。
- 此欄位建立後不會改變：方案的來源不會從線上變成教練開立，反之亦然。

### `bookings(package_id)` 索引

```sql
CREATE INDEX IF NOT EXISTS idx_bookings_package ON bookings(package_id);
```

線上單堂方案會讓方案筆數大幅增加，方案與預約之間的查詢（列方案時統計已上完／已約堂數、作廢連動、新的方案頁）都靠這個欄位。索引要在 `package_id` 欄位確定存在之後才建（既有資料庫的這個欄位是 `addColumnIfMissing` 補的，不在 `CREATE TABLE` 裡）。

### 不變量

上線並補登完成後，下列條件恆成立，由服務層維持並有測試：

- 每一筆 `status = 'confirmed'` 的預約 `package_id` 都不是 NULL。
- `source = 'online'` 的方案 `total_sessions = 1`，`remaining_sessions` 只會是 0 或 1。
- `source = 'online'` 的方案在同一時間最多只有一筆 `confirmed` 預約。

`package_id` NULL 的預約仍會存在（上線前就已取消的舊預約），所有程式仍須能處理 NULL，不能假設一定有方案。

## 線上單堂方案的生命週期

以下把 `source = 'online'` 的方案稱為「線上單堂方案」。

### 建立

`createBookingAnon` 在同一個交易裡：建預約 → 寫入金額與折扣 → 建線上單堂方案 → 把預約的 `package_id` 指向它。

| 方案欄位 | 值 |
|---|---|
| `member_id` | 主客人（一對二的同行客人不另建方案，與「錢只算主客人」一致） |
| `session_type` | 與預約相同 |
| `total_sessions` | 1 |
| `remaining_sessions` | 0（那一堂已經約了） |
| `amount` | 實付金額＝`original_amount − discount_amount` |
| `discount_code` | 與預約相同 |
| `source` | `online` |
| `created_by` | NULL |
| `created_at` | 當下本地時間（`nowLocal()` 格式） |
| `expires_at`、`note` | NULL |

- 不使用既有的 `createPackage()`：它會把剩餘堂數設成總堂數，還會對金額再套一次折扣碼。新增一個只給這條路用的內部函式。
- 預約本身的欄位照舊：`original_amount` 仍是定價、`discount_amount`／`discount_code` 仍記在預約上、`paid_at` 仍是 NULL 等待核對。**不會**像教練登錄那樣自動蓋已付款。
- 管理者用線上入口補登過去日期的課，一樣產生線上單堂方案。

### 核對收款、改時段、設定同行

不影響方案，行為與現在相同。

### 取消

所有取消路徑（客人自己取消、教練取消、管理者取消、Google 日曆刪除事件、整批取消、取消並退款、整批取消並退款）目前都經過 `refundPackageForBooking()` 回補 1 堂。線上單堂方案在回補之後多一步判斷：

| 被取消的那筆預約 | 方案結果 |
|---|---|
| 還沒付款（`paid_at` NULL） | 方案作廢（寫 `archived_at`） |
| 已付款、未退款 | 方案保留，`remaining_sessions = 1`，可由教練登錄改約 |
| 已付款、這次就是「取消並退款」 | 方案作廢 |

教練／管理者開立的方案（`staff`）取消行為完全不變。

**折扣碼用量**（我的判斷）：現在每條取消路徑都會釋放該預約的折扣碼用量（`releaseRedemption`）。線上單堂方案改成跟著方案走——方案保留 1 堂時不釋放（折扣後的金額還留在那 1 堂上，之後會以折扣價改約），方案作廢時（未付款取消、退款、作廢）才釋放方案名下所有預約的用量。否則限用一次的折扣碼會被同一位客人用兩次。教練開立的方案與沒有方案的舊預約，取消時照舊釋放。

### 一筆錢只對應一張方案

付款與退款目前記在預約上（`paid_at`、`refunded_at`）。保留的那 1 堂被改約之後，同一張線上單堂方案會有兩筆 `paid_at` 有值的預約：原本被取消的那筆，和改約後的那筆（教練登錄會蓋 `paid_at`）。兩筆對應的是同一筆錢。

所以線上單堂方案的金錢狀態以**方案**為單位判斷（我的判斷）：

- 付款狀態（顯示用）：名下沒有任何預約有 `paid_at` → 待核對；有預約有 `paid_at`、沒有預約有 `refunded_at` → 已核對；有預約有 `refunded_at` → 已退款。
- 一張線上單堂方案只能退款一次。

### 退款

`refundBookingAdmin`／`refundBookingGroupAdmin` 處理的預約如果掛在線上單堂方案上，多三個檢查與一個後續動作：

| 情況 | 結果 |
|---|---|
| 方案已作廢（已經退過款，或那 1 堂已被作廢放棄） | 拒絕，`409 package_closed`，訊息「這堂已經退款或已作廢」 |
| 要退的是已取消的那筆，但方案上另有一筆 `confirmed` 預約（那 1 堂已被改約用掉） | 拒絕，`409 credit_in_use`，訊息「這堂已經改約，請對改約後的那一堂退款」 |
| 其餘（預約已付款、未退款） | 照現有流程：預約若還是 `confirmed` 就取消，寫 `refunded_at`，通知客人；**之後把方案作廢**，並釋放方案名下預約的折扣碼用量 |

這樣不論中間取消、改約幾次，同一筆錢最多退一次。

退款入口有兩個：

- 後台「已核對匯款」清單長按（現有）。這個清單只留最近 50 筆。
- 會員方案區的單堂卡上新增「退款」按鈕（我的判斷：保留的那 1 堂可能很久之後才退，清單裡已經找不到）。按鈕呼叫現有的 `POST /api/admin/bookings/:id/refund`，對象是卡片上顯示的那筆預約。只有方案未作廢、且付款狀態是已核對時才出現。

### 保留的那 1 堂被改約使用

教練在登錄預約選到這張線上單堂方案時，走現有的 `createCoachRegister`：扣 1 堂、建預約、蓋 `paid_at`、`original_amount`＝方案單價（＝當初實付金額）。不需要新程式，但要有測試。之後這筆新預約再被取消、退款，套用上面同樣的規則。

### 改客人／方案（`reassignBooking`）

（我的判斷。）

- **未付款**的線上單堂預約：可以改掛到任何客人的任何方案，與現在相同。原本的線上單堂方案回補後立刻作廢，這一步要在「舊方案先用」的判斷**之前**完成，否則回補後它會暫時變成可用，把改掛擋下來。
- **已付款**、掛在線上單堂方案上的預約（包含用保留的 1 堂改約出來的那筆）：不能改掛，回 `409 paid_online_single`，前端訊息「這堂線上預約已付款，不能直接改客人或方案。要改請先取消（會保留 1 堂），或由管理者退款。」

不讓已付款的改掛，原因是現有的改掛會把預約移到新方案、把 `paid_at` 改成當下，原本那張線上單堂方案就變成「剩 1 堂、名下沒有任何預約」，卡片沒有東西可顯示，退款規則也碰不到它。「舊方案先用」擋不住這種情況：它只看 id 比目標方案小的方案，而線上單堂方案的 id 通常比客人原有的方案大。

### 後台對線上單堂方案可做的事

（我的判斷：線上單堂方案是預約的鏡像，手動操作越少越不會出現對不上的狀態。）

| 動作 | 線上單堂方案 |
|---|---|
| 改單價 | 可以（管理者）。見下 |
| 退款 | 可以（管理者）。條件與結果見「退款」一節 |
| 作廢 | 只有「保留的那 1 堂、沒有未取消的預約」時可以，意思是**不退款、這 1 堂失效**（例如臨時取消不退費）。作廢時釋放折扣碼用量，不通知客人。有未取消的預約時回 `409 has_active_booking`，前端提示改用「取消預約」 |
| 還原 | 不提供，API 回 `409 online_single_readonly` |
| 調整剩餘堂數 | 不提供，API 回 `409 online_single_readonly` |

有未取消預約時不讓直接作廢的原因：現有的方案作廢會靜默取消名下預約，不通知客人與教練、不釋放折扣碼用量；線上預約應該走正常的取消流程。

作廢與退款的差別要在確認視窗寫清楚：退款會記錄退款時間並通知客人；作廢不記退款、不通知，之後也不能再對這張方案退款。

### 改單價

`updateUnitPrice` 目前把方案名下 `confirmed` 預約的 `original_amount` 改成新單價，但不動 `discount_amount`。教練開立的方案這個欄位本來就是 NULL，所以沒問題；線上單堂預約如果用過折扣碼，改單價後薪資會變成「新單價 − 舊折扣」，等於折了兩次。

改法：改單價時，同一批預約的 `discount_amount` 與 `discount_code` 一併清成 NULL，並釋放該預約的折扣碼用量（與 `reassignBooking` 轉方案時的處理一致）。語意是「管理者指定的單價就是最後的金額」。對教練開立的方案沒有實際影響。

| 方案作廢連動取消（`archivePackage`） | 靜默取消名下預約 | 教練開立的方案不變；線上單堂方案見上表 |

## 會員方案區的單堂卡

`GET /api/coach/packages?memberId=` 每筆方案多回：

- `source`
- 線上單堂方案另附 `single`：
  - 代表預約：方案名下 `confirmed` 的那筆；沒有就取 id 最大的那筆。回它的 `booking_id`、`start_at`、教練名稱、預約狀態。
  - 付款狀態：以方案為單位（見「一筆錢只對應一張方案」），回 `pending`／`paid`／`refunded` 與實付金額。
  - 可退款的預約 id：按「退款」時要送的那一筆（代表預約已付款就用它；否則取名下已付款、未退款、id 最大的那筆）；不能退款時為 NULL。

`renderMemberPackages` 對線上單堂方案改用單堂卡呈現：

- 左欄購買日與時間（與現有方案卡相同位置）。
- 標題：一對一／一對二＋「線上單堂」標記＋狀態（已預約／已上完／已取消／保留 1 堂／已作廢）。
- 內容：上課時間、教練、金額、付款狀態（待核對／已核對／已退款）。
- 動作：依上面的表（改單價；符合條件時退款、作廢）。

排序維持購買時間新到舊，與教練開立的方案混排。「方案（套餐）」標題與「＋新增方案」不變。視覺沿用現有 `.pkg-row` 樣式與 `DESIGN.md` 的規則，不新增顏色。

## 補登既有資料

一次性執行，位置在伺服器開機、開始接受請求之前。

1. 檢查 `app_settings` 的 `online_single_backfill_done`，是 `'1'` 就略過。
2. 先用既有的備份機制做一份資料庫快照。快照失敗就不補登、不設旗標，下次開機再試。快照檔名要和每週備份區分，避免被輪替刪掉。
3. 在單一交易內，對每一筆 `status = 'confirmed' AND package_id IS NULL` 的預約：
   - 建一張線上單堂方案，欄位同「建立」一節，差別只有：`created_at` 用該預約的建立時間。`bookings.created_at` 是 UTC 的 `YYYY-MM-DD HH:MM:SS`，要轉成本地時間的 `YYYY-MM-DDTHH:MM:SS`。`original_amount` 是 NULL 的舊預約，方案 `amount` 也是 NULL。
   - 把預約的 `package_id` 指向新方案。
   - 預約的其他欄位一律不動（金額、折扣、付款、時間都不改）。
4. 寫入旗標與結果摘要（補登筆數、涉及會員數、執行時間）到 `app_settings`。
5. 全程不呼叫任何通知。

已取消的預約不補（規則 7）。帶 `recurring_group_id` 的舊散客循環，每一堂各補一張。

冪等：條件是 `package_id IS NULL`，就算旗標遺失重跑也不會重複建立。

補登的方案 id 會比實際購買時間晚（id 是新的，`created_at` 是舊的）。#150 與續購提醒都用 id 當購買順序：

- 續購提醒已排除線上單堂，不受影響。
- #150 只看還可用的方案。補登當下這些方案全是剩 0 堂，不受影響。之後若某一筆補登過、已付款的預約被取消而留下 1 堂，這 1 堂在先用順序裡會被當成「補登當天才買的」，排在客人原有的同類型方案之後。（我的判斷：接受這個順序。受影響的只有「上線時還沒上、已付款、客人同時有教練開立的同類型方案、之後又被取消不退款」的預約，數量極少，結果只是晚一點才用到那 1 堂。改用購買時間排序要動剛上線的 #150，而且舊方案的時間格式不一致，風險比好處大。）
- 上線後新建立的線上單堂方案，id 就是實際順序，沒有這個例外。

之後若有新功能要用 id 判斷購買順序，要記得補登的線上單堂方案是例外。

## 測試

除了現有測試全數通過，至少新增：

- 線上預約後：方案存在、欄位正確、預約指向它、`paid_at` 仍為 NULL。有折扣碼、一對二有同行客人各一例。
- 取消的每一條路徑 × 未付款／已付款：方案結果符合表格。
- 折扣碼用量：已付款取消後用量仍算已用；未付款取消、退款、作廢後釋放。
- 退款：已付款未取消、已付款已取消、保留的 1 堂已被改約（對原筆退款被拒）。
- 退款只能一次：改約後的那筆「取消並退款」後，原筆不能再退；改約後的那筆只取消，兩筆之中退了一筆，另一筆不能再退；作廢後不能退。
- 保留的 1 堂由教練登錄改約：金額、付款狀態正確；改約後再取消、再退款。
- 改客人／方案：未付款線上單堂改掛成功、舊方案作廢、不被「舊方案先用」誤擋；已付款的被擋（同客人、不同客人、不同類型各一例）。
- 舊方案先用：線上單堂（剩 0）不擋 10 堂方案；上線後建立、保留的 1 堂比之後才買的同類型方案先用；補登方案留下的 1 堂排在原有方案之後。
- 續購提醒：10 堂剩 1 堂的客人另有一筆未來的線上單堂 → 照樣提醒。
- 客人端我的方案：不含線上單堂方案。
- 薪資：線上單堂標「散客」、金額不變；補登前後各期輸出相同。
- 改單價：有折扣碼的線上單堂改單價後，薪資金額＝新單價。
- 後台動作限制：線上單堂的調整、還原、有未取消預約時的作廢都被擋；單堂卡的付款狀態與「可退款的預約」在各種取消／改約組合下正確。
- 補登：筆數正確、冪等、不發通知、已取消的不補、`original_amount` NULL 的舊預約可補、時間換算正確。
- 既有測試裡直接用 SQL 建立、沒有方案的預約仍能正常取消與計薪（NULL 仍被容忍）。
