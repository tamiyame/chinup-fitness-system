# Google 日曆過去堂連動（刪除→取消、移動→改期） — 設計規格

- 日期：2026-08-12
- 狀態：業主已核可設計
- 取代：`2026-07-04-gcal-pull-sync-design.md` 的「過去堂保護」政策（該規格其餘部分不變）

## 背景與決策翻轉

反向同步（PR #85）原政策：**過去堂的移動與刪除一律忽略**，理由是「在 Google 日曆整理歷史事件不該悄悄動到已結算的薪資」。實際營運三十餘天後業主拍板翻轉：

> Google 日曆整理歷史事件的行為，其實就跟我在系統內取消是一樣的。重點是連動，我不需要每次都進到系統做這件事情。

系統內取消（`cancelBooking`）與改期（`rescheduleBooking`）本來就**沒有過去堂限制**——過去堂取消照樣回補堂數、從薪資口徑移除。Google 端是同一位操作者的另一個入口，語意應一致。實際踩到的兩案：8/3 過去堂在日曆上拖到 8/10 沒反應（移動被守門擋）、8/11 兩筆當日已開始的一對一在日曆上刪除沒取消（刪除被守門擋）。

## 目標

Google 日曆上對系統事件（`chinupbk` 前綴）的人為異動，**不分過去未來堂**一律連動：

- **刪除** → 自動取消（回補堂數＋釋放折扣＋薪資口徑排除），管理者通知、客人教練靜默——與現行未來堂刪除同一條路。
- **移動** → 套用既有驗證（整點、60 分鐘、不撞課）後改期（客人收改期通知）；不合法退回＋教練通知。
- 「不可移到過去」規則改為**只對未來堂生效**（原意是防未來堂被誤拖進過去瞬間變已上課）；過去堂允許移到過去（修正歷史紀錄）或未來（延期補課）。

DB 贏、回聲防護、syncToken 機制、通知模板全部不變。

## 變更點（全在 `src/services/gcalPull.js` 的 `processEvent`；服務層、schema、API 零改動）

依現行程式行號：

1. **刪除分支**（`:69`）：刪掉 `if (b.start_at <= now) return;`。過去堂刪除照走 `cancelBookingFromGcal` ＋ `notifyAdmins('gcal_delete_cancelled')`。`cancelBookingFromGcal` 守門（存在、`status='confirmed'`）、回補、釋放折扣、清 `gcal_event_id` 對過去堂原樣適用，零改動。
2. **全天事件退回**（`:86`）：`if (b.start_at > now)` 條件刪除——過去堂事件被改成全天同樣退回（DB 贏對過去堂也成立）。
3. **移動忽略守門**（`:91`）：刪掉 `if (b.start_at <= now) return;`。
4. **不可移到過去**（`:93`）：`if (evStart <= now)` 改為 `if (b.start_at > now && evStart <= now)`——僅未來堂禁止移入過去；過去堂移動目標不限過去未來，僅受整點／60 分／撞課檢查。
5. **檔頭註解**（`:1-3`）：政策描述更新（刪「過去堂一律不理」），規格引用補本文件。
6. **事件描述文案**（`gcalSync.js` `buildEventBody`）：「可直接拖動改時段：需整點起、60 分鐘、未來時段；刪除事件＝取消預約並回補堂數」→「可直接拖動改時段（整點起、60 分鐘）；刪除事件＝取消預約並回補堂數」。既有事件文字待下次寫入時自然更新，不做回補。

## 語意彙總（改後）

| 日曆操作 | 未來堂 | 過去堂（改後） |
|---|---|---|
| 刪除事件 | 取消＋回補＋管理者通知（客人教練靜默） | **同左**（原：忽略） |
| 拖動到合法時段 | 改期＋客人通知 | **同左**（原：忽略）；目標可為過去或未來 |
| 拖動到過去 | 退回「不可移到過去」＋教練通知 | 視為合法目標（走整點／60 分／撞課檢查） |
| 非整點／非 60 分／撞課／全天 | 退回＋教練通知 | **同左**（原：忽略） |
| 系統自身異動的回聲 | 跳過 | 跳過（不變） |

## 邊界與保護

- **可見範圍是 Google API 的天生限制**：syncToken 只回報「上次基準同步 `timeMin`（基準日−1 天）之後」的事件異動。410 重基準後窗口起點會前移到「重基準日−1 天」，更早的過去事件在日曆上的異動不會回報——要保證生效需進系統操作。此為 API 行為，不另做補償。
- **不追溯**：已被 token 消化的歷史異動（含 8/11 兩筆刪除）不會因本次部署重放；那兩筆由業主在後台取消一次。**不**清 token 強制重基準——「事件被刪但預約有效」的歷史堂可能存在（PR #91 colorBackfill 即為此刻意跳過 404/410 不復活），寬窗重基準會把它們誤取消。基準 `timeMin = 現在−1 天` 維持不變，410 重基準最多重放一天內的刪除，且與新語意一致（刪除＝取消）、回聲防護兜底。
- **薪資影響即所求**：過去堂取消／改期會改動當期（或已結算期別）薪資口徑，與系統內操作同語意，屬業主明示要的行為；管理者通知與 `cancel_reason='gcal_event_deleted'` 留稽核。
- reconcile（5 分鐘兜底）只處理未來事件，不受影響；不復活過去事件的既有行為不變。

## 測試（tests/gcal-pull.test.js 增修；GCAL_MOCK=1）

原案例 6「過去堂忽略」翻面，矩陣如下：

1. 過去堂刪除 → 預約 cancelled、`cancel_reason='gcal_event_deleted'`、方案 remaining +1、`gcal_event_id` 清空、管理者收 `gcal_delete_cancelled`、客人教練無通知。
2. 過去堂移動→過去合法時段（整點、60 分、無撞）→ 改期套用、客人收 `booking_rescheduled`、無 updateEvent。
3. 過去堂移動→未來合法時段 → 同上（8/3→8/10 案例）。
4. 過去堂移動→非整點 → 退回（updateEvent body=DB 時間）＋教練收 `gcal_move_rejected`。
5. 過去堂事件被改全天 → 退回。
6. 未來堂移到過去 → 仍退回「不可移到過去」（回歸案例，行為不變）。
7. 既有其餘案例（回聲、未來堂刪除、token 泵…）全數不變、必須續過。

- 過去堂刪除的客人通知（沿用靜默＋管理者稽核）。
