# 套裝方案改成「一列一個套裝」（A 版）設計

日期：2026-11-17
取代：`2026-11-17-package-plan-catalog-design.md` 的「價目表」版面與資料形狀（C 版）。開會員方案的其餘行為不變。

## 為什麼要改

C 版的價目表是「堂數 × 類型」一格一個價，同類型同堂數只能有一個價格。業主上線當天就遇到限制：一堂要有好幾種價格、十堂也要有好幾種價格（例如原價與舊生價）。他從當初的四個版面裡改選 A（清單＋下拉選單），並同意下面的規則。

版面畫布：https://claude.ai/artifact/AThj6TifZAPEBGpyr5b5c4

## 這頁管的是什麼

「賣什麼」的規格目錄：一列就是一個可以賣的套裝。不是「誰買了什麼」的紀錄。

## 業主同意的規則

1. 一個套裝＝類型（一對一／一對二）、堂數、每堂單價、名稱（可空）、啟用與否。同類型同堂數可以建好幾筆。
2. 名稱用來分辨同堂數的不同價格（「舊生價」「體驗價」）。清單上是堂數旁的小標籤；選單裡顯示成「一對一 10 堂・舊生價・每堂 NT$1,300」，沒有名稱就是「一對一 10 堂・每堂 NT$1,400」。
3. 停用＝暫時不出現在選單，可再啟用；刪除＝整筆拿掉（在編輯側欄裡，要確認）。兩者與改價都只影響之後新開的方案。
4. 「新增方案」是一個下拉選單：先顯示「請選擇套裝」，最後一項是「自訂（自己輸入堂數與單價）」。選自訂才出現類型、堂數、每堂單價。金額那一行沿用 #155 的樣式（左算式、右總額大字）。
5. 後台會員彈窗與教練登錄預約彈窗用同一個選單。
6. 套裝只有管理者能新增、修改、停用、刪除；教練只能選用。
7. 正式站已經填的價目自動轉成一筆一筆的套裝（名稱空白、啟用中）。

我自己決定、已告知業主的三件事：

- 排序固定：一對一在前、堂數少到多、同堂數價格高的在前；不能手動調順序。
- 會員的方案紀錄只記堂數與金額，不記也不顯示套裝名稱。`customer_packages.from_plan` 維持 1／0／NULL 的旗標。
- 類型、堂數、單價、名稱四項完全相同的套裝不能重複建。

## 資料

`package_plans` 改成：

| 欄位 | 說明 |
|---|---|
| `id` | 主鍵，沿用原本的值 |
| `session_type` | `'1on1'`／`'1on2'` |
| `total_sessions` | > 0 |
| `unit_price` | > 0 |
| `name` | 可空；存入前去頭尾空白，空字串存成 NULL；最多 20 個字 |
| `is_active` | 0／1，預設 1 |
| `created_at` | 建立時間 |

拿掉 `UNIQUE (session_type, total_sessions)`。SQLite 拿不掉既有的唯一鍵，所以開機時整表重建一次（偵測訊號：沒有 `is_active` 欄位）；舊資料原 id 照搬、`name` 是 NULL、`is_active` 是 1。沒有任何表指向 `package_plans`。`app_settings.package_plans_version` 不再使用，留著不動。

## 端點

| 端點 | 權限 | 說明 |
|---|---|---|
| `GET /api/coach/package-plans` | 教練 | 回 `{ plans }`，只有啟用中的，已排序。兩個「新增方案」入口用 |
| `GET /api/admin/package-plans` | 管理者 | 回 `{ plans }`，含停用的。「方案」頁籤用 |
| `POST /api/admin/package-plans` | 管理者 | 新增一筆，回 201 與該筆 |
| `PATCH /api/admin/package-plans/:id` | 管理者 | 改任意欄位（沒送的不動）；停用／啟用也走這裡 |
| `DELETE /api/admin/package-plans/:id` | 管理者 | 刪除，回 `{ ok: true }` |

原本整張取代的 `PUT /api/admin/package-plans` 拿掉。

套裝物件：`{ id, sessionType, totalSessions, unitPrice, name, isActive }`（`name` 沒有時是 `null`）。

錯誤碼：`invalid_session_type`、`invalid_total`（1–200）、`invalid_unit_price`（1–1,000,000）、`invalid_name`（不是字串或超過 20 字）、`invalid_active`（不是布林）皆 400；`too_many_plans`（已有 100 筆）400；`duplicate_plan` 409；`plan_not_found` 404。

`POST /api/coach/packages` 多收 `planId`：

- 有 `planId`：必須是正整數（否則 400 `invalid_plan_id`）。套裝不存在或已停用 → 409 `plan_not_available`；類型、堂數、或折扣前金額（單價 × 堂數）對不上 → 409 `plan_price_changed`。通過後 `from_plan = 1`。同時送 `fromPlan: false` 視為矛盾 → 400 `invalid_from_plan`。
- 沒有 `planId` 但 `fromPlan: true`（還沒重新整理的舊畫面）：改用類型＋堂數＋金額比對啟用中的套裝；沒有這個類型＋堂數的套裝 → 409 `plan_not_available`，有但金額都對不上 → 409 `plan_price_changed`。
- `fromPlan: false` → `from_plan = 0`；沒送 → NULL。與現在相同。

## 畫面

**後台「方案」頁籤**：標題「套裝方案」＋「＋ 新增套裝」。一行摘要「共 N 個・啟用中 M 個。會員的「新增方案」只會列出啟用中的。」清單依類型分組，每列：「一對一 10 堂」、名稱標籤、狀態點（啟用中／已停用）、每堂、總價、「編輯」「停用／啟用」。手機上每列排成兩行（第二行是算式與按鈕），摘要只留「共 N 個・啟用中 M 個」。沒有資料時顯示空狀態。

**側欄**（共用 `#drawer`）：類型兩顆按鈕、堂數、每堂單價（可打千分位）、試算、名稱（可空）與說明、啟用勾選、說明文字、「儲存」「取消」；編輯時右邊多一顆「刪除」。欄位錯誤在儲存時提示並把焦點移到該欄。

**「新增方案」選法**（`public/package-plan-picker.js`，兩個入口共用）：下拉選單＋（選自訂時）類型按鈕與兩個輸入框＋金額列。沒有任何啟用中的套裝時，兩個入口維持改版前的自訂表單、不送 `fromPlan`（與現在相同）。伺服器回 `plan_price_changed`／`plan_not_available` 時提示「套裝剛更新過，請重新選擇」並重新讀取選單。

## 不做的事

- 手動排序、套裝分類、期限、每個套裝的銷售統計。
- 在會員的方案紀錄上記錄或顯示套裝名稱。
- 改價紀錄。

## 驗證

- API 測試：權限（教練不能改、未登入 401）、五個端點、開方案帶 `planId`。
