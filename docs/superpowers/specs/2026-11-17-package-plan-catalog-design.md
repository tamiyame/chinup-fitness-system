## 為什麼

現在開方案的做法是：管理者或教練打開某位會員，在「＋ 新增方案」裡自己輸入堂數和每堂單價。每次都靠人打，工作室「賣哪幾種方案、各多少錢」沒有一個地方可以統一管理。

業主要的結果（2026-11-17 原話整理）：

1. 「方案」獨立出來：管理者先建好套裝方案，例如一對一 10 堂、一對二 10 堂、一對一 20 堂。
2. 會員的「新增方案」可以直接選建好的套裝，也保留自己輸入堂數和單價的做法。
3. 以後預設都用套裝；有例外情況，教練或管理者才自己輸入。

## 兩個名詞

這份文件裡兩個詞指不同的東西，不要混用：

- **套裝方案**：工作室賣的規格，由「類型＋堂數＋每堂單價」組成。存在價目表裡，跟任何會員無關。這次新增的就是它。
- **會員方案**：某位會員買下的那一筆（`customer_packages` 的一列），有剩餘堂數、到期日、名下預約。現有功能，這次只多記一個「是不是照價目表開的」。

## 現況

- 會員方案由 `POST /api/coach/packages`（教練與管理者都能用）建立，欄位：會員、類型、總堂數、總金額、到期日、備註、折扣碼。總金額＝畫面上的每堂單價 × 堂數；單價留空就建立「無單價」方案；有折扣碼時以折後總額入帳。
- 開方案的入口有兩個，表單各寫一份：
  - 後台會員編輯彈窗的「方案（套餐）」區：`public/admin.js` `renderMemberPackages` 裡的「＋ 新增方案」。
  - 教練「登錄預約」彈窗：`public/coach.js` `regmNewPkgFormHtml`／`bindRegmNewPkgForm`（客人沒有可用方案時直接出現，或按「＋ 新增方案」展開）。這個入口沒有備註欄。
- 系統裡沒有任何「套裝方案」的資料表或設定。單堂價格（一對一 1500／一對二 2000）是另一組設定，放在「折扣碼」頁籤，只給線上預約用。
- 後台頁籤：課程、報名作業、會員、教練、折扣碼、通知、LINE 管理、薪資計算、報價單。後台整頁只有管理者進得來。

## 目標

- 後台多一個「方案」頁籤，內容是一張價目表：每一列是一種堂數，兩欄是一對一、一對二，格子裡填每堂單價。
- 兩個「新增方案」入口都改成先選套裝：點類型、再點堂數，堂數和單價照價目表帶入。
- 兩個入口都保留「自訂」：欄位與現在相同，教練和管理者都能用。
- 還沒建任何套裝時，兩個入口的表單與現在完全相同。

## 不做的事

- 跨會員的方案清單、搜尋與篩選（舊文件第二階段的內容，連同當時列在那一節的保留堂數總覽、補登快照刪除入口，都不在這次範圍）。
- 套裝名稱、同一種「類型＋堂數」有多種價格、統計每種套裝開出幾份。
- 套裝帶使用期限。業主 2026-11-17 確認：套裝不帶期限，開會員方案時的「到期日」維持選填。
- 客人端的任何畫面。客人不會看到價目表，也不能自己線上買套裝。
- 線上自助預約的單堂、單堂價格設定（仍在「折扣碼」頁籤）。
- 會員方案既有的規則：堂數扣抵與回補、同類型舊方案先用、續購提醒、薪資、調整堂數、改單價、作廢與還原。
- 在會員方案列上標示「套裝」或「自訂」（資料會記，畫面不顯示，見「我的判斷」）。

## 絕對不能發生的事

- 上線後、價目表還是空的時候，開方案的做法跟今天有任何不同。
- 改了價目表，已經開給會員的方案金額跟著變。
- 教練照畫面上的套裝價開出方案，實際入帳的卻是另一個價格（例如管理者剛好在同一時間改了價）。
- 教練或管理者因為沒有對應的套裝而開不出方案。「自訂」永遠可用。
- 非管理者改得到價目表。

## 業主確認的規則

2026-11-17 業主已確認（第 1–3、5 條是他明確說的；其餘是我提出、他看過後選版時沒有異議）：

1. 管理者先建套裝方案，獨立成後台的「方案」頁籤。
2. 「新增方案」預設用套裝；例外才由教練或管理者自己輸入堂數和單價。
3. 版面選 C：價目表＋「類型／堂數」兩步選。
4. 套裝的內容只有類型、堂數、每堂單價；總價自動算。
5. 套裝不帶使用期限；開會員方案時的到期日照現在選填。
6. 只有管理者能改價目表；教練只能選用。
7. 選了套裝，堂數和單價就照價目表，不能在表單上改；要調價用折扣碼，或改用自訂。
8. 改價目表只影響之後新開的會員方案。
9. 還沒建任何套裝之前，「新增方案」的表單和現在一模一樣。
10. 教練登錄預約彈窗的「＋ 新增方案」用同一種選法。線上自助預約的單堂不受影響。

版面 C 帶來的限制，業主選版時已看過：同一個「類型＋堂數」只有一個價格。特價用折扣碼或自訂處理。

## 資料庫結構

兩處變更都只新增，不改、不刪既有資料。

### 新資料表 `package_plans`

| 欄位 | 型別 | 說明 |
|---|---|---|
| `id` | INTEGER 主鍵 | |
| `session_type` | TEXT NOT NULL | `'1on1'` 或 `'1on2'`，有 CHECK |
| `total_sessions` | INTEGER NOT NULL | 堂數，CHECK > 0 |
| `unit_price` | INTEGER NOT NULL | 每堂單價（元），CHECK > 0 |
| `updated_at` | TEXT NOT NULL | 本地時間，與全站一致（`nowLocal()`） |

`UNIQUE(session_type, total_sessions)`：一個組合只有一列。「不提供」的組合就是沒有那一列。

沒有任何資料表指向這張表，所以整張表可以隨時重寫，不影響既有會員方案。

寫進 `src/db/schema.js`（`CREATE TABLE IF NOT EXISTS`）。

### `customer_packages.from_plan`

新增可空的整數欄位：

- `1`：照價目表開的。
- `0`：教練或管理者用自訂開的。
- `NULL`：這個功能上線前的舊方案，以及線上單堂方案（`source = 'online'`）。

記的是「開立當下的方式」，之後管理者改單價也不回頭改這個值。

加法：`schema.js` 的建表語句加上這一欄；`src/db/connection.js` 用現有的 `addColumnIfMissing('customer_packages', 'from_plan', 'INTEGER CHECK (from_plan IN (0, 1))')` 補到既有資料庫。既有列一律是 `NULL`。

## 後端

### 價目表

- `GET /api/coach/package-plans`（教練與管理者）
  回 `[{ sessionType, totalSessions, unitPrice }]`，依堂數小到大、同堂數一對一在前。
- `PUT /api/admin/package-plans`（只有管理者）
  內文 `{ plans: [{ sessionType, totalSessions, unitPrice }] }`，代表**整張價目表**：送來的就是儲存後的全部內容，沒送的組合會被移除。整批在一個交易裡完成，任何一筆不合格就整批不存。回傳格式與 `GET` 相同。

  驗證與錯誤碼（HTTP 400）：
  - `plans` 不是陣列，或超過 60 筆 → `invalid_plans`
  - 類型不是 `1on1`／`1on2` → `invalid_session_type`
  - 堂數不是 1–200 的整數 → `invalid_total`
  - 單價不是 1–1,000,000 的整數 → `invalid_unit_price`
  - 同一個「類型＋堂數」出現兩次 → `duplicate_plan`

  空陣列合法，代表清空價目表。

（60、200、1,000,000 是我的判斷：夠用，又擋得住打錯多幾個零。）

### 開會員方案

`POST /api/coach/packages` 多收一個選填欄位 `fromPlan`（布林）。其他欄位與行為不變。

- 沒帶或是 `false`：與現在完全相同，另外把 `from_plan` 記成 `0`。
- `true`：
  1. 用送來的類型＋堂數查價目表。查不到 → HTTP 409 `plan_not_available`。
  2. 送來的 `amount` 必須等於價目表的每堂單價 × 堂數。不相等或沒帶 → HTTP 409 `plan_price_changed`。
  3. 通過後照現有流程建立（折扣碼照樣以這個總額去折），`from_plan` 記成 `1`。

第 2 步是為了「絕對不能發生的事」第三條：畫面上的價目表可能是幾分鐘前載入的，伺服器用當下的價目表再核一次，對不上就不開，請使用者重選。

`createOnlineSingleForBooking`（線上單堂）不動，`from_plan` 維持 `NULL`。

會員方案的查詢結果（`GET /api/coach/packages` 等）會多帶 `from_plan` 欄位，前端這次不使用。

## 後台「方案」頁籤

位置：頁籤列「會員」的右邊，文字「方案」。內容照畫布 C 的電腦與手機兩張。

### 內容

- 標題「套裝方案價目表」。說明文字：「直接在格子裡打每堂單價，總價自動算。有填價格的組合，才會出現在會員的『新增方案』。」
- 一張表：第一欄堂數，後面兩欄「一對一」「一對二」。列依堂數小到大。
- 每個格子是一個每堂單價輸入框（前面有「NT$」）。下方小字：有填 →「共 NT$14,000」（單價 × 堂數）；留空 →「不提供」。
- 表格下方兩顆按鈕：「＋ 新增堂數」「儲存價目表」。
- 最下方說明：「價格留空＝不提供這個組合；一整列都留空再儲存，這個堂數就會移除。改價只影響之後新開的方案，已經開給會員的不會變。」

### 行為

- 「＋ 新增堂數」在表格最下面加一列，堂數是可以輸入的數字框，兩個價格格子空白。已儲存過的列，堂數顯示成文字、不能改；要換堂數就新增一列、把舊的那列清空。（我的判斷。）
- 所有修改先留在畫面上，按「儲存價目表」才一次送出（`PUT`）。有還沒儲存的修改時，按鈕旁顯示「有未儲存的變更」。
- 儲存前在畫面上先檢查，並指出是哪一格：堂數要是 1–200 的整數、不能跟別列重複；單價要是 1–1,000,000 的整數。新增的列如果填了價格卻沒填堂數，也算錯誤。
- 儲存成功：提示「價目表已儲存」，表格依伺服器回傳的結果重畫（兩格都空的列消失、依堂數重新排序）。
- 價目表是空的時候：表格位置顯示一行「還沒有套裝方案。按『＋ 新增堂數』開始建立。」，兩顆按鈕照常。
- 手機與電腦是同一張表（三欄在 390px 寬放得下，見畫布手機那張）。
- 載入失敗、儲存失敗沿用後台現有的錯誤提示方式。

### 外觀

照 `DESIGN.md`：髮絲線分隔、數字用 Archivo＋tabular-nums、單一天藍強調色、輸入框字級 16px。只用後台現有的元件樣式（`.a-sec-head`、`.form-input`、`.btn`、`.btn-primary` 等），不新增視覺語彙。

## 「新增方案」的選法

兩個入口用同一套選法。每次表單出現時向 `GET /api/coach/package-plans` 取最新的價目表。

### 價目表有內容時

依序是：

1. **類型**：兩顆並排的按鈕「一對一」「一對二」，預設選「一對一」（與現在下拉選單的預設相同）。
2. **堂數**：一排選項，列出這個類型在價目表上有價格的堂數（小到大），例如「10 堂」「20 堂」「30 堂」，最後固定一顆「自訂」。
3. 選了某個堂數：下方顯示「10 堂 × NT$1,400 ＝ 總額 NT$14,000」；有選折扣碼時後面接「（套用折扣碼後以折後總額入帳）」，與現在相同。堂數和單價在這個狀態下沒有輸入框。
4. 選了「自訂」：出現「堂數」「每堂單價（可空）」兩個輸入框，試算文字與現在相同（單價留空 →「未填單價 → 建立為『無單價』方案」）。
5. 其餘欄位不變：到期日（可空）、折扣碼、備註（可空；教練登錄彈窗本來就沒有這一欄）、「建立方案」。

細節：

- 一打開時堂數沒有任何一顆被選。沒選就按「建立方案」→ 提示「請先選堂數」。（我的判斷：跟錢有關，不替使用者預選。現在的表單堂數也是空白、要自己填。）
- 切換類型時，堂數選項換成該類型的；原本選的若是「自訂」就維持自訂、已輸入的數字保留，否則清掉選取。
- 某個類型在價目表上一個價格都沒有：堂數那排只剩「自訂」，並且直接選上。
- 送出：選套裝時帶 `fromPlan: true`、`totalSessions`＝選的堂數、`amount`＝單價 × 堂數；選自訂時與現在送的內容相同（不帶 `fromPlan`）。
- 伺服器回 `plan_price_changed` 或 `plan_not_available`：提示「價目表剛更新過，請重新選擇」，重新取價目表並重畫選項，其他已填的欄位（到期日、折扣碼、備註）保留。
- 建立成功後的行為與現在相同（後台：重新載入會員方案區；教練彈窗：帶著新方案回到登錄流程）。

### 價目表是空的時候

表單與現在完全相同：類型下拉、堂數、每堂單價（可空）、到期日、折扣碼、（備註）、建立方案。送出內容也相同。取價目表失敗時同樣退回這個表單，不擋開方案。

### 程式放哪裡

選法的畫面與邏輯寫成一個前端共用模組，兩個入口都引用，不各寫一份。兩頁的樣式表是分開的（`admin.html`、`coach.html` 各有自己的 inline CSS），樣式怎麼共用由實作者決定。

## 測試

後端（比照現有 `tests/package-*.test.js`、`tests/online-single-migration.test.js` 的寫法）：

- 價目表：空表回空陣列；`PUT` 後 `GET` 的內容與排序；再 `PUT` 一份較少的 → 沒送的組合消失；空陣列清空；每一種驗證錯誤各回對應錯誤碼且整批不存（原內容不變）。
- 權限：非管理者的教練 `GET` 成功、`PUT` 被拒；未登入兩者都被拒。
- 開方案帶 `fromPlan: true`：成功 → 金額＝單價 × 堂數、`from_plan = 1`；加折扣碼 → 金額是折後總額、`from_plan = 1`；價目表沒有那個組合 → 409 `plan_not_available`；`amount` 對不上或沒帶 → 409 `plan_price_changed`；兩種 409 都沒有新增任何會員方案。
- 開方案不帶 `fromPlan`：行為與現在相同、`from_plan = 0`；單價留空的「無單價」方案照樣能開。
- 改價目表後，先前開出的會員方案 `amount` 不變。
- 線上預約自動建立的單堂方案 `from_plan` 是 `NULL`。
- 資料庫升級：在沒有 `from_plan` 欄位、沒有 `package_plans` 表的舊結構資料庫上開機 → 欄位與表都補上，既有會員方案的 `from_plan` 是 `NULL`，其他欄位不變；重複開機不出錯。
- 全套既有測試維持上線前的結果。

前端（本機實際操作，電腦寬度與 390px 各一次）：

- 「方案」頁籤：新增堂數、填價、儲存、重新整理後內容還在；清空一格 → 該組合消失；清空一整列 → 該堂數消失；重複堂數與不合格的價格被擋下並指出位置。
- 後台會員彈窗與教練登錄彈窗各走一遍：價目表為空時表單與現在相同；有內容時選套裝開方案、選自訂開方案、切換類型、某類型沒有套裝時只剩自訂。
- 開著表單時另開視窗改價，再回來按建立 → 出現「價目表剛更新過，請重新選擇」，沒有開出方案。
- 以教練（非管理者）身分登入，登錄彈窗看得到套裝、開得出方案。
